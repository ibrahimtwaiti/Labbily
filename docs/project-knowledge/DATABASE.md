# Database and tenant boundaries
Observed main migrations 001_initial.sql through 016_agent_action_approval.sql; PostgreSQL schema plus SQLite local support. Main agent migrations: 012 studio, 013 inbox workspace, 014 jobs, 015 retrieval, 016 action approval. Pending #41: 017 focused workspace, 018 task calendar, 019 workspace controls. File numbering is not necessarily schema version: focused release notes state 017 -> schema 16; verify db.py migration registry and actual environment version before applying. 017 adds profiles, history, stages, segments and flow/run tables; 019 inspected CREATE TABLE campaign_images, workspace_teams, workspace_team_members, workspace_fields, contact_field_values, inbox_preferences, wa_template_drafts. No claim these are applied in prod.
- Production and staging isolated; pooled runtime DATABASE_URL, direct DATABASE_URL_UNPOOLED only for approved migrations/restore in trusted operator context. Never copy production data into Codex, staging or CI. Local SQLite not a production substitute. Use migrations, not ad hoc SQL.
- Check tenant ID from authenticated context; tenant-scoped indexes, constraints, composite ownership where appropriate; enforce authorization of related entities, private object access, queues and AI knowledge. Test two tenants, cross-tenant IDs, duplicate webhooks, simultaneous quota reservations, deletion and restore.
- Migration plan: identify baseline and target versions, verify backup and restore to disposable database, test old/new code compatibility, document rollback and forward fix; never assume dropping tables is safe. Preserve event/idempotency history.
- Existing docs describe shared relational model; no evidence of server-per-tenant. Do not change deployment tenancy without owner decision. Live physical DB configuration, counts, roles, indexes and RLS coverage were not inspected during handover; do not claim RLS as sole safeguard.
